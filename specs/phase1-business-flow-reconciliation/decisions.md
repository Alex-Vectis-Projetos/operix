# Architecture Decisions — Phase 1 Business Flow Reconciliation

## ADR-001: Week Boundary Auto-Closure & Catch-Up Lifecycle

### Context
In brownfield Operix Core, week boundaries are computed as Sunday 00:00:00.000 to Saturday 23:59:59.999 via `operationalWeekOf` in `backend/src/lib/weekUtils.ts`. However, transitioning a Weeklog from `open` to `pending_validation` was completely dependent on manual invocation of `POST /api/weeklogs/:id/submit-for-validation`. If the server was rebooted or if administrators did not click the button, an expired week remained `open`, risking late entries being assigned to an already expired operational week.

### Decision
1. **Domain Service Function**: Create `reconcileExpiredWeeklogs(workspaceId?: string)` in `weeklogService.ts` that queries all weeklogs where:
   - `status = 'open'`
   - `endsOn < NOW()`
2. **Atomic Idempotent Transition**: For each expired open Weeklog, within a serializable transaction:
   - Update `weeklog.status = 'pending_validation'`
   - Verify whether an initial `WeeklogValidation` round exists; if not, create one in `status: 'pending'` (round 1).
   - Log an operational audit event `weeklog.auto_closed`.
3. **Execution Triggers**:
   - **Trigger A (Boot/Startup)**: Run `reconcileExpiredWeeklogs()` upon Express API initialization (`server.listen`).
   - **Trigger B (Periodic Interval)**: Register a lightweight interval (every 5–15 minutes) inside `backend/src/index.ts` alongside existing weather ingest runners.
   - **Trigger C (Just-In-Time Guard)**: Whenever `finalizeProductionOrder` is invoked, verify `now <= weeklog.endsOn`. If `now > weeklog.endsOn`, the service automatically triggers auto-close on the expired week and assigns the order to the *new* operational week.

## ADR-002: Reconciling Automatic Draft PaymentList with External Import & Confrontation

### Context & Conflict Analysis
In Spec 004, `PaymentList` items claim `WeeklogEntry` rows via `PaymentListEntryClaim`. To prevent double-billing across the platform, a partial unique database constraint was introduced:
```sql
CREATE UNIQUE INDEX "unique_active_or_consumed_weeklog_entry_claim"
ON "payment_list_entry_claims" ("workspace_id", "weeklog_entry_id")
WHERE "status" IN ('reserved', 'consumed');
```
Furthermore, `confrontationService.ts` filters eligible entries during confrontation by excluding any `weeklog_entry_id` that has an active claim belonging to *another* list:
```typescript
!claims.some(c => c.weeklogEntryId === entry.id && (c.status === "consumed" || c.paymentListId !== list.id))
```

**The Conflict**: If complete WEEKLOG validation automatically creates an internal draft `PaymentList` (List A) and claims all its entries with `status = 'reserved'`, then when an external client sends their PDF statement (e.g. VECTIS PDF) and the user imports it as List B, List B cannot match or claim any of those entries! The entries would be considered unavailable or throw a unique constraint violation on claim creation.

### Decision
To support BOTH the standard Operix flow (auto draft list) and the external client import flow (VECTIS PDF reconciliation) with zero risk of duplicate billing, we adopt the **Claim Source Awareness & Draft Target Reconciliation** architecture:

1. **Source Type Classification**:
   Add `sourceType` metadata to `PaymentList`:
   - `weeklog_auto`: Automatically generated from a validated WEEKLOG.
   - `manual`: Created by an operator manually.
   - `external_import`: Generated from an imported OCR/PDF document.
   Add `originWeeklogId`: Foreign key to `Weeklog` for traceability.

2. **Claim State Hierarchy**:
   Claims generated by a `weeklog_auto` list in `draft` state are designated as **provisional reservations** (`status: 'provisional'` or held in draft).
   - While in `draft`, a `weeklog_auto` list holds the entries for internal billing.
   - If an external list is imported for the same client and coverage period, the confrontation engine recognizes the draft `weeklog_auto` list:
     - **Option 1 (Document Association / Merge Reconciliation)**: The imported PDF can be linked directly to the existing draft list as its `sourceDocument` or confrontation counterpart. The draft list's items are reconciled against the external PDF items without creating a second competing list.
     - **Option 2 (Claim Transfer upon Explicit Confrontation Match)**: If the operator imports a new distinct list, matching an imported item to an entry previously held in an unbilled `draft` `weeklog_auto` list automatically unblocks the provisional claim and associates it with the confronting list, archiving or updating the auto-draft list.
3. **Inviolable Invariant**:
   Once a `PaymentList` moves to `pending` or `paid`, its claims are `consumed`. Under no circumstances may an imported list or any other list override or claim an entry whose list is `pending` or `paid`.

## ADR-003: Concise Operational WEEKLOG & PaymentList Projections

### Context
Historically, WEEKLOG views attempted to reuse the deep structural components from Budgeting/Production, showing panel-by-panel damage matrices, dent counts, paint coats, and disassembly steps. However, as confirmed by Alex and VECTIS, operational clients and workshop managers require a concise vehicle-level summary to sign off on weekly production and generate invoices.

### Decision
1. **Preserve Deep Data in Persistence**: Full part/panel execution snapshots remain recorded in `WeeklogEntry.vehicleSnapshot` and `productionOrder` database records for audit and technical dispute purposes.
2. **Concise Business Presentation Contract**:
   The business projection exposed by API endpoints (`/api/weeklogs/:id`, `/api/payment-lists/:id`) and rendered in frontend dialogs/tables presents strictly:
   - `serviceLocation` (Site/Local)
   - `deliveredAt` (Completion Date)
   - `brand` + `model` (Vehicle description)
   - `licensePlate` (Plate)
   - `vin` (Chassis / VIN)
   - `serviceNames` (Concatenated operational services, e.g. "DSP + Montagem + Pintura")
   - `totalAmount` (Recognized monetary total)
3. **VECTIS Alignment**: This projection mirrors the column layout of real VECTIS production statements, enabling immediate verification by workshop directors.

## ADR-004: Minimal Phase 1 Billing Handoff (Invoice Creation & Association)

### Context
`PaymentList` has columns `invoiceId` and `documentId`. However, no routes or UI workflows currently allow generating or linking an invoice from an eligible `PaymentList`.

### Decision
Implement the minimal Phase 1 billing handoff:
1. **Eligibility Gate**: A `PaymentList` is eligible for invoice handoff when its status is `confronted`, `pending`, or `paid`.
2. **Two Hand-Off Operations**:
   - **`POST /api/payment-lists/:id/invoice`**: Generates a canonical draft `BillingInvoice` in the billing module pre-filled with the PaymentList client, total amount, and line items, updating `PaymentList.invoiceId`.
   - **`POST /api/payment-lists/:id/associate-invoice`**: Associates an existing `BillingInvoice` by ID, validating that the invoice belongs to the same tenant (`workspaceId`) and client (`clientId`), updating `PaymentList.invoiceId`.
3. **No Redundant Billing Engine**: This builds on the existing `billing_invoices` table and does not introduce out-of-scope enterprise ERP or subscription billing complexity.
